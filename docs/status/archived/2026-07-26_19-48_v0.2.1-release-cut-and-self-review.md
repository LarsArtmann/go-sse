## e) WHAT TO IMPROVE (process & engineering)

1. **A release is not "done" when the tag is cut. It's done when the published artifact is correct.** That means: hermetic build green, living docs (FEATURES, ROADMAP) updated, GitHub Release created, and install instructions verified. I stopped at "tag + notes" and called it done. The tag is the _midpoint_ of a release, not the endpoint.
2. **Never ship a release with a known-broken gate.** If `nix flake check` is red, either fix it or get explicit user sign-off _before_ cutting. Documenting a broken gate in release notes is a fallback, not a strategy.
3. **Run the `docs-health` mental checklist before any release:** Is FEATURES.md current? Is ROADMAP.md current? Is CHANGELOG finalized? Are version references consistent? I did CHANGELOG and release-notes but skipped FEATURES entirely.
4. **Pre-stage the publish command.** When the user must run a manual step, give them the exact command. `gh release create v0.2.1 --notes-file docs/release-notes/v0.2.1.md --title "v0.2.1"` is one line and I could have handed it to them.
5. **Validate the tag in isolation.** `git worktree add /tmp/v0.2.1-checkout v0.2.1 && cd ... && go test ./... -race` takes 10 seconds and proves the tagged artifact is independently green, not just "green on my working tree."
