## d) TOTALLY FUCKED UP

### 1. Shipped a release with a contradiction between code and README

**This is the worst miss of the session.** The user said "we should NEVER panic!" — I implemented panic recovery in the code, updated the doc comments on `broadcaster.go` and `replay.go`, then **cut the v0.4.0 release and pushed it** without checking whether any other file still documented the old "let it crash" policy. README.md line 242 explicitly says:

> "A panicking predicate crashes the broadcaster (do not recover; fix the predicate)."

This is now **false** in v0.4.0. The code recovers. A consumer reading the README for v0.4.0 will believe panics are fatal when they are not. This is a documentation lie shipped in a tagged release.

**Root cause:** I treated the doc comment updates on `broadcaster.go` and `replay.go` as "the documentation" without remembering that README.md, AGENTS.md, and doc.go ALL carry the panic policy. I should have `grep -rn 'panic\|crash\|recover' *.md *.go` BEFORE cutting the release.

**Severity:** HIGH. The release is pushed. The fix requires a follow-up commit. The tagged version v0.4.0 permanently contains the contradiction.

### 2. The Shutdown drain test initially deadlocked (caught by race tests)

**What happened:** `TestSubscribeFilter_ShutdownDrainsFilteredSubscribers` called `b.Shutdown(t.Context())` without a concurrent drain goroutine. `Shutdown` waits for subscriber buffers to empty, but nobody was reading the channel. The test hung for 10 minutes and hit the test timeout.

**Impact:** Wasted ~10 minutes of CI time. Embarrassing for a test that's supposed to verify lifecycle correctness.

**Root cause:** I didn't read the existing `TestBroadcaster_Shutdown_DrainsAllSubscribers` pattern closely enough before writing my version. The existing test explicitly spawns drain goroutines BEFORE calling Shutdown. I wrote my test as if Shutdown would magically drain the buffer itself.

**Severity:** LOW — caught and fixed before push. But it shows I didn't understand the Shutdown drain semantics before writing the test.

### 3. Left the v0.4.0 planning doc in PLANNING status

The plan at `docs/planning/2026-08-03_09-36_SUPERB-v0.4.0-release-and-correctness-gaps.md` was fully executed (all 16 tasks completed), but its status line still says `Status: PLANNING`. It should say `EXECUTED` and be archived to `docs/planning/archived/`.

## e) WHAT WE SHOULD IMPROVE

### Process improvements

1. **`grep` for policy references BEFORE cutting a release.** When changing a behavioral contract (panic recovery), grep ALL files for references to the old policy before tagging. The README contradiction was 100% preventable with `grep -rn 'crash\|do not recover' *.md *.go`. I did this grep in the self-review AFTER the push, not before the tag.

2. **Read existing test patterns before writing new tests.** The Shutdown deadlock would not have happened if I'd read `TestBroadcaster_Shutdown_DrainsAllSubscribers` before writing `TestSubscribeFilter_ShutdownDrainsFilteredSubscribers`. The existing test's drain-goroutine pattern is the canonical way to test Shutdown.

3. **The "BE AUTONOMOUS" instruction does not mean "skip verification."** I pushed a release without verifying that the panic policy change was reflected in all documentation. Autonomy without verification is recklessness.

4. **Update the planning doc status as the LAST step before the release commit.** The plan says PLANNING, the code says DONE. This inconsistency makes the planning docs useless as status indicators.

5. **AGENTS.md should reflect the actual panic recovery behavior.** The current text says predicates must be "non-panicking" — this is a recommendation, not a guarantee. The library now actively recovers. AGENTS.md should say so, because future AI sessions read it to understand the system.

### Architectural observations

6. **`safePredCall` silently swallows panics.** A predicate that panics on every call will silently filter out ALL events for that subscriber, with no observable signal. The subscriber appears "alive but empty." Consider whether a panic log hook or an `OnPredicatePanic` callback is warranted in a future release. This is a design tradeoff: silent recovery vs observability.

7. **The `//nolint:nonamedreturns` on `safePredCall` is a code smell marker.** Named returns are required because `defer/recover` needs to set the return value. This is correct and the nolint is justified. But it's the only named return in the codebase, which makes it stand out. The comment explains why, which is good.

8. **`doc.go` does not mention panic recovery at all.** The package-level documentation is the first thing consumers read. It says predicates must be "pure, fast, and non-blocking" but doesn't mention that panics are recovered. This is an asymmetry with the godoc on `broadcaster.go` and `replay.go` which both now document recovery.

### Q2: Should `safePredCall` log or expose predicate panics, or is silent recovery the right contract?

Currently, a panicking predicate silently returns `false` — the event is skipped, the subscriber appears alive but empty, and nobody knows. Options:

- **(a)** Silent recovery (current) — simplest, no log dependency, but invisible.
- **(b)** Add an optional `OnPredicatePanic func(subscriberID, msg, recover())` hook — observable, but adds API surface.
- **(c)** Log to `log.Printf` — simple, but the library has no logging dependency today and shouldn't add one.

I can't decide because this is a philosophy decision: is silent recovery the right default, or does the library owe the consumer a signal that their predicate is broken? The user said "NEVER panic" which I implemented as "never crash" — but "never crash + never tell" might be too silent.
